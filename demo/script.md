## The spec

> So what is a demo, if nobody records it? It is a file that sits beside your code.

> This is the whole thing. It opens by naming the app, the address to visit, and the size of the window to film it in.

> Then the steps, in order. Click this. Wait for that. It reads like a description of the demo, because that is exactly what it is.

## Byte-identical, every time

> Here is the property everything else in this tool rests on.

> That is the checksum of the video we just rendered. Now run exactly the same command again.

> Same spec, same app, same bytes. Not similar — identical.

> A virtual timeline and a frozen clock mean nothing drifts between runs: not a slow network, not a faster machine, not the time of day.

## When the app changes

`04-when-the-app-changes.reel.yaml` · 8 lines · 188 words

> Now the part that decides whether a demo is worth keeping. Products change.

> Check re-runs the whole demo headlessly. No rendering, no video — just the question: does every step still do what it says?

> So let us change the product. Someone renames a navigation item from Listings to Marketplace — one word, in the app's real source.

> And the demo breaks. Not vaguely — it names the step, the selector that no longer resolves, and writes out the page and the screenshot from the moment it gave up.

> Nobody had to notice. In continuous integration this is a red build, instead of a picture quietly showing a button that no longer exists.

> Then heal. It re-resolves the broken step against the app as it is now, looking for the control that means the same thing rather than the one that happens to sit in the same place.

> It found the renamed item, finished the run, and wrote the repair back into the spec — a one-line diff you review like any other change.

> Green again. The demo survived a change to the product, and nobody re-recorded anything.

## Every deliverable, one recording

`06-every-deliverable.reel.yaml` · 4 lines · 118 words

> One demo is never one video.

> There is a long one for the docs, a minute for a feed, forty seconds for the top of a readme. Written as separate specs they drift apart within a month — someone fixes a caption in one and forgets the other three.

> So a cut is not a second recording. It names a range of the demo you already filmed — by beat, not by timestamp, so inserting a step earlier cannot silently shift what a cut contains.

> Four deliverables, each at its own size and frame rate, out of a single drive of the app. They cannot disagree with each other about what happened, because they are the same frames.

## In CI

`07-in-ci.reel.yaml` · 4 lines · 101 words

> Everything so far runs the same way on a continuous integration runner, with no service to sign up for and nothing to host.

> One command runs every demo in the repository and reports a single result. A step that cannot complete is a failing build.

> On a pull request it writes one comment, updated in place rather than added to, so a long-running branch does not collect a column of stale bot noise.

> And because the renders are deterministic, regenerating the media is a no-op unless the demo really changed. A picture that moves in a diff means the product moved.

## Studio

> Everything you have seen is the command line, because that is the whole tool. But you do not have to live there.

> Studio runs on your machine, from your project directory. Nothing is uploaded, and there is no account. This is every spec in the workspace, with whatever each one last rendered.
